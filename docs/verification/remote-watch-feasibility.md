# #9 원격 변경 감시 타당성

Windows 11 Pro 빌드 26300의 네이티브 Herdr App 0.1.18과 core 0.1.22에서 Debian 13.8 QEMU 게스트의 ext4를 열었다. 게스트 커널은 `6.12.118+deb13-cloud-amd64`, 사용자 UID는 1000이었다. `enp0s2` 송신에 netem 20ms를 적용했다. 지연 측정의 두 실행에서 지속 SSH 연결로 각 25회 확인한 응용 계층 RTT 중앙값은 21.30ms와 21.65ms였다. 네이티브 프레임은 1600×1025였다. [#9 기준](https://github.com/kalstein00/herdr-swift-tree/issues/9)

## 같은 구성에서 유휴와 단일 변경 측정

1. Windows의 같은 Herdr 창에서 SSH space의 합성 루트 `WatchProbe9`와 `Left`, `Right`를 연다. `Left`에 `ALDERRENAME.txt`, `base-left.txt`, `Right`에 `base-right.txt`를 둔다. 실험의 기반은 `995c6ba6e9e806fe77b3aef97dc60b2e62eb8e87`이다.
2. 설치한 실험 Mod는 `exec(..., { on: space.machine, timeout: 8000 })`으로 기존 core의 SSH 연결에서 `sh`를 실행한다. 한 배치에서 아래 명령으로 루트와 두 폴더의 장치·inode·mtime·ctime을 읽는다. 100ms 간격으로 최대 20회 확인한다. 직전 응답에서 받은 값이 달라지면 즉시 반환한다. 바뀐 열린 폴더만 기존 디렉터리 조회 경로로 다시 읽고 새 값을 다음 요청에 전달한다.

   ```sh
   LC_ALL=C TZ=UTC stat -L --printf '%d:%i:%y:%z\n' -- "$@"
   ```

3. 초기 목록이 보인 뒤 30초 동안 두 폴더를 펼친 채 둔다. 게스트에서 실제 목록 열거와 메타데이터 실행 완료를 각각 기록한다. 이후 똑같은 SSH space, 폴더, 실험 코드로 파일 생성·삭제를 번갈아 각 25회, 이름 변경을 25회 실행한다. 파일 작업 사이 간격은 800ms다.
4. 별도의 지속 SSH 연결에서 합성 파일을 변경한다. Windows에서 보낸 명령 직전과 성공 응답 수신 직후의 QPC 값을 남긴다. 게스트에서 수행한 작업 성공 시점은 이 사이에 있다. Windows Graphics Capture의 첫 결과 프레임 QPC와 두 값을 비교해 지연 범위를 구한다. 이름 변경은 이전 이름이 사라지고 새 이름이 나타나는 프레임을 고른다. 각 p95는 25개 값의 24번째 순위로 계산한다.

## 관측 결과

원격 감시가 없던 기반에서는 게스트의 생성·삭제·이름 변경이 성공하고 각각 1.25초 이상 지난 뒤에도 Windows의 기존 목록이 남았다. 해당 상태를 실제 창에서 확인하고 게스트 목록을 별도로 열거했다.

같은 열린 폴더의 실험 경로에서는 30.000초 동안 목록 조회가 0회였다. 해당 구간에 응답을 마친 메타데이터 요청은 14회였고, 이 응답에 기록된 `stat` 실행은 280회였다. 한 실행에서 폴더 3개를 확인해 총 840개의 폴더 메타데이터 확인이 있었다. 초기 목록 3회 이후 파일 작업으로 변경된 `Left`의 목록은 75회 읽었다.

게스트 인터페이스 전체의 전송량은 수신 20,092바이트와 송신 16,594바이트였다. OpenSSH의 유효 설정은 `ServerAliveInterval 0`, `TCPKeepAlive yes`였다. Core 소스는 연결에 기본 15초 heartbeat를 보낸다. 게스트의 목록 호출 기록을 읽어 조회 횟수를 판정했고, 연결 유지 패킷만의 바이트 수는 계측 범위 밖이었다. [core heartbeat 구현](https://github.com/herdrdev/herdr-core/blob/329cb66ebce5eca3d917fcf7364a099046979b49/crates/herdr-core/src/server.rs#L290-L293) · [원격 연결 수신](https://github.com/herdrdev/herdr-core/blob/329cb66ebce5eca3d917fcf7364a099046979b49/crates/herdr-core/src/remote.rs#L376-L384)

| 작업 | 표본 | 지연 p95 하한–상한 | 상한 최대 |
| --- | ---: | ---: | ---: |
| 생성 | 25 | 363.87–385.70ms | 418.14ms |
| 삭제 | 25 | 335.01–357.28ms | 361.12ms |
| 이름 변경 | 25 | 339.55–362.04ms | 362.05ms |

75개 작업 모두에서 결과 프레임을 찾았다. 성공 시점의 범위와 화면 지연 계산에는 Windows QPC를 사용했다. 새 이름과 남은 파일이 보이는 마지막 화면을 독립 게스트 목록과 대조했다. 화면과 원시 타임라인, 실험 Mod, 게스트 추적, 분석 도구는 작업의 로컬 `ticket-9` 아티팩트에 보관했다.

## 제품화 범위

| 경로 | 성능과 배포 부담 |
| --- | --- |
| Herdr core와 GNU `stat` | 이 구성에서 두 목표를 충족했다. 이미 등록한 연결과 서버 도구를 사용한다. 열린 폴더 수에 따라 메타데이터 작업량이 증가하고, 중단 후 목록을 대조해야 한다. |
| 별도 Linux Helper | 지속 inotify로 유휴 메타데이터 반복을 줄이고 유실 신호를 얻을 수 있다. Helper의 사용자 권한 배포, 버전 관리, 연결 복구 및 성능을 별도로 검증해야 한다. |
| Herdr upstream 변경 | 기존 연결에 원격 파일 이벤트를 추가하고 Mod에 전달할 수 있다. App/core의 API, 호환성 및 배포 일정이 필요하다. 이 경로의 화면 지연은 측정하지 않았다. |

기존 core 경로를 첫 제품 후보로 채택한다. 이번 판정은 소규모 ext4 실험의 두 목표에 한정한다. 다수 폴더, 대량 변경, 끊김·복구, 실제 서버의 배포 및 설치 후보 성능은 후속 검증 대상이다. [ADR 결정](../adr/0001-remote-helper.md) · [소스 계약](../research/remote-watch-contracts.md)
